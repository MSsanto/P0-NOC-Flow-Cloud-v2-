# Homologação — v0.2.0-alpha

Escopo: **desenvolvimento/demo local e teste**. Este roteiro não autoriza produção, exposição pública ou Azure.

## Pré-condição

Use a `main` atualizada e somente dados sintéticos.

```powershell
git checkout main
git pull
docker compose down -v
docker compose up -d --build
docker compose ps
```

Esperado: `postgres`, `backend` e `web` ativos/saudáveis.

## 1. Saúde e documentação

Abra:

- `http://localhost:8000/api/v1/health/live`
- `http://localhost:8000/api/v1/health/ready`
- `http://localhost:8000/api/v1/docs`

Esperado: health `200` e Swagger acessível.

## 2. Criar incidente sintético

Abra `http://localhost:4200/incidents` e registre:

- Título: `WAN indisponível — DEMO S2`
- Recurso: `DEMO-S2-EDGE-01`
- Severidade: `HIGH`
- Impacto: `OUTAGE`
- Sintomas: `Conectividade indisponível no recurso sintético de homologação.`
- Início: horário atual ou passado

Esperado:
- criação concluída;
- status inicial `OPEN`;
- ID gerado pelo servidor;
- incidente visível no detalhe/lista;
- nenhum campo para `tenant_id`, ator ou status inicial.

## 3. Timeline inicial

No detalhe, localize **Timeline**.

Esperado:
- evento `Incidente criado`;
- ator de demonstração exibido;
- data/hora exibida;
- ausência de erro/loading persistente.

## 4. Registrar atualização

Em **Atualizar incidente**, informe:

`Operadora acionada; protocolo DEMO-S2-001.`

Esperado:
- feedback de sucesso;
- contexto do incidente preservado;
- timeline passa a conter `Atualização registrada` após o evento de criação;
- mensagem, ator e horário visíveis.

Teste negativo: mensagem apenas com espaços ou menor que 3 caracteres deve ser bloqueada.

## 5. Filtros, ordenação e paginação

Volte para `/incidents`.

Valide:
- filtro `Status = OPEN`;
- filtro `Severidade = HIGH`;
- período contendo o incidente criado;
- ordenação por `Atualização — mais recente`;
- botão **Limpar**;
- metadados `Exibindo X–Y de Z` e `Página N de M` quando houver resultados;
- navegação Anterior/Próxima quando houver mais de 25 itens.

Teste negativo: defina início do período posterior ao fim. A UI deve bloquear a consulta e informar o problema.

## 6. Normalizar incidente

Abra novamente o incidente e clique em **Normalizar incidente**.

Antes da confirmação, espere uma etapa explícita de confirmação. Informe opcionalmente:

`Conectividade restabelecida e validada.`

Confirme.

Esperado:
- status muda para `RESOLVED`;
- timeline recebe `Incidente normalizado`;
- observação/ator/horário ficam visíveis;
- controles de nova atualização/normalização deixam de estar disponíveis para o estado resolvido.

## 7. Negativos de lifecycle via Swagger

No Swagger, usando o ID do incidente já resolvido:

1. `POST /api/v1/incidents/{id}/normalize` novamente com `{}` → esperado `409`.
2. `POST /api/v1/incidents/{id}/updates` com `{"message":"Atualização inválida pós-resolução."}` → esperado `409`.

## 8. Consulta avançada via Swagger

Teste:

```text
GET /api/v1/incidents/query?status=RESOLVED&severity=HIGH&page=1&page_size=25&sort=updated_at&order=desc
```

Esperado:
- `200`;
- body com `items`, `page`, `page_size`, `total`;
- incidente sintético presente se corresponder aos filtros.

Teste parâmetros inválidos:
- `page=0` → `422`;
- `page_size=101` → `422`;
- `sort=title` → `422`;
- período invertido → `422`.

## 9. Regressão Sprint 1

Confirme que ainda funcionam:
- lista simples;
- criação;
- detalhe;
- refresh do navegador mantendo persistência;
- 404 para UUID inexistente sem crash da UI.

## 10. Encerramento

Após homologar:

```powershell
docker compose down -v
```

O `-v` remove o banco de teste local.

## Critério de decisão

**APROVADA — LOCAL/TESTE** quando todos os passos acima forem satisfeitos e não houver BLOCKER/MAJOR/Critical/High aberto para o escopo suportado.

**APROVADA COM RESSALVAS** somente para problema não bloqueante documentado e sem impacto nos critérios P0.

**REPROVADA** se houver falha de persistência, tenant scoping, lifecycle, timeline, filtros essenciais, regressão Sprint 1, build/test/audit ou smoke full-stack.

## Limite de release

Mesmo após homologação manual, a `v0.2.0-alpha` **não está autorizada para produção ou exposição pública**. OIDC/RBAC e identidade confiável continuam pendentes para incremento posterior. Nenhuma tag/GitHub Release é requisito para este gate técnico.
