# Homologação — v0.1.0-alpha

**Projeto:** P0 — NOC Flow Cloud v2  
**Escopo:** Sprint 1 — Fundação Executável  
**Tipo de release:** alpha local/teste  
**Produção:** NÃO AUTORIZADA  
**Data:** 2026-09-10

## Objetivo

Validar de forma reproduzível que a candidata `v0.1.0-alpha` executa o primeiro vertical slice do produto com Angular, Nginx, FastAPI e PostgreSQL: **listar → criar → visualizar detalhe de incidente**.

## Pré-condições

- Docker Desktop/Engine em execução;
- Docker Compose disponível;
- portas locais `4200`, `8000` e `5432` livres;
- working tree baseada na `main` homologada;
- nenhum dado corporativo real usado no teste.

## 1. Preparar ambiente limpo

```bash
git checkout main
git pull
docker compose down -v
docker compose up -d --build
```

Aguardar até:

```bash
docker compose ps
```

Resultado esperado:

- `postgres`: healthy;
- `backend`: healthy;
- `web`: healthy.

Se algum serviço não ficar saudável:

```bash
docker compose logs --no-color
```

A homologação deve ser interrompida e classificada como **REPROVADA** até correção.

## 2. Health e documentação da API

Abrir no navegador:

- `http://localhost:8000/api/v1/health/live`
- `http://localhost:8000/api/v1/health/ready`
- `http://localhost:8000/api/v1/docs`

Esperado:

- live: HTTP 200;
- ready: HTTP 200 e banco disponível;
- Swagger abre e lista os endpoints da API v1.

## 3. Homologação visual — lista

Abrir:

`http://localhost:4200/incidents`

Validar:

- título/estrutura da página são exibidos;
- botão/link para registrar incidente existe;
- estado vazio é compreensível quando não há registros;
- não há erro de API no carregamento;
- layout não cria rolagem horizontal indevida em janela estreita;
- navegação por `Tab` alcança as ações principais.

## 4. Criar incidente válido

Selecionar **Registrar incidente** e preencher somente dados fictícios, por exemplo:

| Campo | Valor de homologação |
|---|---|
| Título | `WAN indisponível — DEMO` |
| Recurso | `DEMO-SJC-EDGE-01` |
| Severidade | `HIGH` |
| Impacto | `OUTAGE` |
| Sintomas | `Conectividade indisponível no recurso fictício de homologação.` |
| Início | horário atual ou alguns minutos no passado |

Acionar **Registrar incidente**.

Esperado:

- nenhum campo de tenant/autor/status é solicitado;
- operação conclui sem erro;
- aplicação navega automaticamente para `/incidents/{id}`;
- status inicial exibido é `OPEN`;
- título, recurso, severidade, impacto, sintomas e horários correspondem ao registro;
- um UUID/ID foi gerado pelo servidor.

## 5. Validar persistência e listagem

Voltar para **Incidentes**.

Esperado:

- incidente recém-criado aparece na lista;
- título, recurso, status, severidade e início são visíveis;
- o incidente pode ser aberto novamente;
- recarregar o navegador (`F5`) não remove o registro, pois ele está no PostgreSQL.

## 6. Validar detalhe e rota

Abrir o incidente e copiar a URL `/incidents/{id}`. Recarregar a página.

Esperado:

- detalhe continua acessível após refresh;
- ID e dados são preservados;
- não há retorno para tela inicial causado pelo refresh.

Também testar um UUID inexistente, por exemplo:

`http://localhost:4200/incidents/00000000-0000-0000-0000-000000000000`

Esperado:

- estado de **Incidente não encontrado**;
- aplicação não quebra e não exibe stack trace.

## 7. Testes negativos do formulário

### Texto composto somente por espaços

Tentar título como `   `.

Esperado: formulário não envia o POST.

### Data futura

Selecionar horário posterior ao momento atual.

Esperado: formulário sinaliza a entrada inválida e não envia o POST.

### Campo obrigatório ausente

Deixar sintomas vazio ou abaixo do limite mínimo.

Esperado: formulário não envia e informa necessidade de revisão.

## 8. Teste negativo da API — authority field

Pelo Swagger em `http://localhost:8000/api/v1/docs`, tentar `POST /api/v1/incidents` acrescentando `tenant_id` ao JSON.

Esperado:

- HTTP `422`;
- registro não é criado;
- o cliente não consegue escolher tenant/ator por body.

Exemplo conceitual inválido:

```json
{
  "title": "WAN indisponível — DEMO",
  "affected_resource": "DEMO-SJC-EDGE-01",
  "severity": "HIGH",
  "impact_type": "OUTAGE",
  "symptoms": "Teste negativo com campo de autoridade forjado.",
  "started_at": "2026-09-10T12:00:00Z",
  "tenant_id": "00000000-0000-0000-0000-000000000000"
}
```

## 10. Segurança e limite de escopo

Para esta alpha:

- dados devem ser sintéticos;
- provider de identidade demo só é aceito em `development`/`test`;
- OIDC/RBAC ainda não existem;
- a aprovação desta homologação **não significa autorização para exposição pública ou produção**.

## Critério de decisão

### APROVADA

Todos os gates técnicos obrigatórios estão verdes, a jornada criar/listar/detalhar funciona e não existe BLOCKER/Critical/High aberto no escopo da alpha.

### APROVADA COM RESSALVAS

A jornada principal funciona, mas existe limitação não impeditiva explicitamente registrada e aceita para a alpha.

### REPROVADA

Qualquer uma das condições abaixo é suficiente:

- build/CI obrigatório vermelho;
- stack não sobe;
- criação/listagem/detalhe falha;
- perda de persistência inesperada;
- migration falha;
- BLOCKER de code review;
- Critical/High de segurança não mitigado;
- documentação contradiz o comportamento executado.
